1. Purpose & Scope
This document is the authoritative backend engineering specification for CreatorIQ. It covers every server-side concern: system architecture, service decomposition, REST API contracts (all endpoints with request/response schemas), database design, ML pipeline design, external integration contracts, security model, infrastructure, error handling strategy, and performance SLAs.
This document is written for the backend and ML engineering teams. It must be read alongside the Frontend PRD (v1.0) to understand the full product context. All API endpoint contracts defined here are the source of truth — the frontend PRD references these, not the other way around.

2. System Architecture
2.1 Architecture Pattern
CreatorIQ uses a modular monolith architecture for the MVP (v1.0), designed to extract into microservices at v2.0. The backend is split into five logical service domains — each deployed as a separate process but within a single AWS ECS cluster. They communicate via internal HTTP (synchronous) and Kafka topics (asynchronous).
This approach avoids the operational complexity of full microservices at MVP scale, while enforcing domain boundaries that enable clean extraction later. Each service domain owns its database schema and must not directly read from another domain's tables.

2.3 Data Flow — Request Lifecycle
Every client request follows this path:
Client sends HTTPS request to the API Gateway (CloudFront + ALB)
API Gateway middleware: validates JWT, checks rate limit, routes to target service
Target service processes request; queries its own PostgreSQL schema
If data is stale or absent, service may: (a) call ML Service for prediction, (b) fetch from Redis cache, or (c) trigger async Kafka job for background refresh
Service returns JSON response in standard envelope to API Gateway
API Gateway forwards response to client

4. Database Schema
All tables use UUID primary keys (gen_random_uuid()). Timestamps use TIMESTAMPTZ (UTC). Soft deletes are used for user-facing records (deleted_at column). Foreign key constraints are enforced at the database level. Each service domain has its own PostgreSQL schema (namespace) within the same RDS instance for MVP.

5. REST API Specification
5.1 API Standards
All endpoints conform to the following standards without exception:
Base URL: https://api.creatoriq.app/v1
Content-Type: application/json on all requests and responses
Authentication: Bearer token in Authorization header (JWT, RS256)
Every response uses the standard envelope:
// Response Envelope
// Success envelope
{ "data": <payload>, "meta": { "request_id": "uuid", "timestamp": "ISO8601" } }
// Error envelope
{ "error": { "code": "ERROR_CODE", "message": "Human-readable message",
             "details": {} }, "meta": { "request_id": "uuid" } }
Pagination: cursor-based. All list endpoints accept cursor and limit (max 100) query params. Response includes next_cursor and total_count in meta.
Versioning: URL path versioning (/v1/). Breaking changes require new version; additive changes (new fields) are non-breaking.
Rate limiting: per user, per endpoint group. Headers: X-RateLimit-Limit, X-RateLimit-Remaining, X-RateLimit-Reset
5.2 Standard Error Codes

// Response 200

// URL includes: client_id, redirect_uri, scope, state (CSRF token), access_type=offline

// POST /auth/youtube/callback
// Request Body

  "state": "string (CSRF token, validated server-side)" }
// Response 200

// 1. Exchange code for access_token + refresh_token via Google Token API
// 2. Encrypt and store tokens in oauth_tokens table

// 4. Create or update channel record
// 5. Enqueue channel.metrics.refresh Kafka event

6. ML Pipeline Specification
6.1 Pipeline Overview
The ML pipeline consists of three independent subsystems: (1) the Data Ingestion Pipeline, (2) the Trend Prediction Engine, and (3) the Content Scoring Engine. Each subsystem runs on its own schedule and produces outputs consumed by the API layer.
6.2 Data Ingestion Pipeline
6.2.1 Google Trends Ingestion
Scheduled cron: every 60 minutes. Uses pytrends library (unofficial) with SerpAPI as failover.
For each niche in the platform's active niche list, fetch interest-over-time for top 50 keywords
Fetch related queries (rising) to surface emerging keyword clusters
Normalize interest scores (0–100) relative to peak within the time window
De-duplicate signals against existing trend_signals records (idempotent writes)
Publish to Kafka topic: trend.signal.ingest
Rate Limit Risk
Google Trends has aggressive rate limits on unofficial access (pytrends). Use SerpAPI (paid) as primary source for production to ensure reliability.
Implement exponential backoff with jitter on all Google Trends requests. Circuit breaker pattern: disable ingestion for 30 minutes after 5 consecutive failures.
Distribute requests across multiple SerpAPI API keys to stay within per-key limits.
6.2.2 YouTube Data API Ingestion
Scheduled cron: every 6 hours. Uses official YouTube Data API v3 (quota cost: ~100 units per run).
Fetch trending videos by region and category (videos.list, chart=mostPopular)
Extract topics from video titles and descriptions using NLP preprocessing step
Match extracted topics to existing trends or create new trend candidates
Track cross-signal convergence: when a topic appears on both Google Trends and YouTube trending, TVS boost applied
Quota management: cache responses in Redis (TTL: 6 hours) to avoid redundant quota consumption
6.3 Trend Prediction Engine
6.3.1 TVS (Trend Velocity Score) Computation
The TVS is recomputed every 2 hours for all active trends. It is a weighted composite of five signals:
Signal Component
Weight
Calculation
Search Volume Acceleration
0.35
Week-over-week growth rate of normalized interest score (Google Trends)
Cross-Platform Convergence
0.25
Presence and growth across multiple data sources (Google + YouTube = max boost)
Historical Peak Lag Pattern
0.20
Comparison against historical patterns for similar topics; measures how far pre-peak we are
Niche-Relative Score
0.15
Topic's relative growth vs niche baseline (isolates niche-specific virality)
Keyword Cluster Breadth
0.05
Number of distinct related keywords showing simultaneous growth
6.3.2 LSTM Forecasting Model
Predicts the interest trajectory for each trend over the next 30 days, generating a confidence interval.
Property
Specification
Architecture
Bidirectional LSTM, 2 layers, hidden size 128, dropout 0.2
Input Features
90-day normalized interest time series + niche encoding (one-hot) + day-of-week + seasonality features
Output
30-day point forecast + 80% and 95% prediction intervals
Training Data

Training Schedule

Serving

Model Registry
MLflow on AWS S3. Automated promotion: new model promoted to production if MASE improvement > 2%.
6.3.3 NLP Classification Model
Classifies trend topics for niche, sentiment, and virality potential.
Base model: distilbert-base-uncased (HuggingFace), fine-tuned on a labeled dataset of 20,000 YouTube trend topics
Classification heads: Niche (multi-label, 24 classes), Sentiment (4-class), Format suitability (long_form/shorts/both)
Input: raw topic string + top 5 related keywords (concatenated)
Output: classification labels + confidence scores per label
Inference: synchronous, integrated into trend ingestion pipeline. P99 latency < 200ms.
Retraining: triggered when > 5,000 new labeled examples accumulate in the feedback table
6.4 Content Scoring Engine
Runs after LLM generation to score generated titles and ideas for predicted performance.
6.4.1 CTR Prediction Model
Model type: XGBoost classifier trained on historical YouTube CTR data from anonymized channel analytics
Features: title length, power word presence, number format presence, question format, sentiment polarity, keyword overlap with trending topics, emoji presence
Output: predicted CTR score 0.0–1.0 (normalized to platform average)
Training: monthly retrain on last 6 months of actual CTR outcomes from consenting Pro+ users
6.4.2 Idea Performance Score
Composite score: 0.4 * trend_tvs_score + 0.3 * ctr_predicted_score + 0.2 * niche_demand_gap_score + 0.1 * format_match_score
niche_demand_gap_score: measures how underserved this topic is in the creator's niche based on view-to-search-volume ratio

Timeout: 15 seconds. On timeout, return status 'failed' with error code GENERATION_TIMEOUT.

Content filter refusal: detect refusal patterns, mark session as 'failed', log for manual review.

9. Authentication, Authorization & Security
9.1 JWT Architecture
Algorithm: RS256 (asymmetric). Public key distributed to all services via internal JWKS endpoint.
Access token expiry: 15 minutes. Refresh token expiry: 90 days (rotated on every use — refresh token rotation).
Access token payload: { sub: user_id, email, plan_tier, channels: [channel_id], iat, exp }
Refresh token: opaque random string (256-bit), stored as bcrypt hash in sessions table. One active session per device.
Token reuse detection: if a revoked refresh token is presented, immediately revoke ALL sessions for that user and alert.
9.2 OAuth 2.0 Security
PKCE (Proof Key for Code Exchange): required for all YouTube OAuth flows
State parameter: CSRF protection — state = HMAC-SHA256(session_id + timestamp), validated on callback
Token storage: OAuth access and refresh tokens stored AES-256-GCM encrypted in the database. Encryption key stored in AWS Secrets Manager. Never logged.
Scope minimization: request only required scopes. Current required scopes: youtube.readonly, yt-analytics.readonly

Mitigation Implementation

LLM data: do not send user PII to LLM APIs. Prompts must contain only content context, never email addresses, real names, or financial data.
